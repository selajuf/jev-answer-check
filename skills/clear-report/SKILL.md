# Понятный отчет

Цель: пользователь быстро понимает результат, его значение, основания
и нужное следующее действие. Основной стиль — ясный русский по принципам
plain language; точность технических сведений сохраняется.

## Общие правила

Перед подготовкой отчета прочитай [контракт](references/contract.md).
Это единая рубрика для автора и проверяющего. Примени ее к текущему запросу
и реальным результатам работы. По вопросу об источниках и выборе подхода
читай [основания](references/sources.md); для обычного отчета они не нужны.

1. Сформулируй главный результат и его значение для пользователя. Опиши
   существенные изменения, их место, имеющиеся проверки и ограничения.
   Добавь следующий шаг, только когда он нужен. При незавершенной работе
   прямо назови состояние и то, что мешает завершению.
2. Пиши по-русски. Заменяй лишний жаргон понятными словами. Сохраняй точные
   имена файлов, команды, код и обозначения API; необходимый специальный
   термин кратко объясни. Убирай повторы, сохраняя смысл, условия и детали.
3. Выбери представление по контракту. Небольшой итог оставь текстом;
   связи или процесс покажи схемой; сравнение — таблицей; числовые данные —
   графиком. Создай HTML, когда совместный просмотр материала, раскрытие
   подробностей или взаимодействие делают сложный результат понятнее.
4. Перед отправкой сверь отчет с критериями контракта. Используй уже
   доступные результаты и разрешенные инструменты. Оформление отчета
   не разрешает дополнительных тестов, публикаций или расходов.

## Codex и Claude Code

Правила одинаковы для обоих агентов. Выбирай доступные в текущей среде
средства: Mermaid для простой схемы, SVG для переносимого изображения,
HTML для страницы с таблицами и визуализациями. В Codex используй нативную
визуализацию, когда она доступна и подходит задаче. В Claude Code можно
создать локальный HTML или воспользоваться установленным `diagram`.
Учитывай инструкции выбранного инструмента.

Graphify используй при подготовке объяснений и отчетов, когда исследование
материалов или карта связей помогают понять результат. Используй готовый
граф и его HTML/SVG; при необходимости исследуй или построй нужный граф.
Для точной компактной схемы по известным данным используй Mermaid.
Видео в этот skill не входит.

В чате оставь краткий итог, существенные ограничения и доступ к созданному
материалу. Сам отчет должен содержать достаточно контекста для понимания
без чтения истории чата. Не публикуй локальный материал автоматически.

## Проверка Jev перед финальным ответом

Перед содержательным отчетом или объяснением вызови MCP `jev_check_answer`.
Возьми `session_id` из контекста hook; передай краткое актуальное задание
в `task_summary`, проверяемый текст в `draft`, нужное содержание материалов
в `artifacts` и имеющиеся свидетельства в `evidence`. Не отправляй полный
транскрипт. Последний запрос и общую рубрику подставляет локальный адаптер.
Если контекста hook нет, передай последний запрос в `last_user_message`:
проверка через MCP доступна независимо от hook, с ограничением двух вызовов
для последнего запроса; изменение краткого задания не сбрасывает лимит.

При `action: rewrite` исправь названные недостатки один раз и снова проверь
исправление, включая измененные материалы. При `keep` сохраняй ответ.
При `uncertain` или `unverified` не заявляй успешную проверку и не создавай
бесконечный цикл. Максимум две оценки на один пользовательский turn.

Jev оценивает; текст и материалы исправляет агент. Он не подтверждает
выполнение команд по одному тексту. Одна ссылка на HTML не дает доступа
к его содержанию. Обычные приветствия и короткие подтверждения не требуют
вызова. Stop-hook — страховка после ответа, а не гарантия скрытой проверки
до показа; основной вызов должен происходить перед финальным сообщением.
