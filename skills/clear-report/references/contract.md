# Контракт понятного отчета

Версия: 1. Основа — принципы plain language из ISO 24495-1:2023,
адаптированные для русскоязычных отчетов агента. Это наш рабочий контракт,
а не официальный перевод стандарта или заявление о сертификации.

## Содержание

Покажи результат и объясни, что он дает пользователю. Для выполненной
работы укажи существенные изменения, их место и имеющиеся подтверждения.
Для исследования отдели выводы от предположений. При частичном результате
или блокере скажи, что готово и что остается сделать.

Условия, влияющие на пригодность результата, должны быть видны сразу:
например, файл подготовлен, но не установлен; изменение внесено, но запуск
не проверен. Следующий шаг нужен, когда пользователь должен что-то решить
или работа требует продолжения. Не добавляй его автоматически.

Все эти сведения не требуют отдельных заголовков. Короткую работу можно
описать несколькими предложениями. Подробный запрос требует подробного
ответа; сокращай повторы, а не нужную информацию.

## Ясный русский

- Начинай с главной мысли. Используй обычные русские слова и прямые действия:
  «изменил настройку», «создал файл», «запрос завершился ошибкой».
- Предпочитай короткие предложения с одной основной мыслью. Сохраняй
  причинные связи, условия и исключения; лимита количества слов нет.
- Одно понятие называй одинаково. Убирай канцеляризмы, рекламные оценки,
  лишние вступления и повтор одного вывода разными словами.
- Заменяй английский жаргон точным русским словом, когда оно есть:
  «резервная копия», «повторный запрос», «настройка». Специальный термин,
  нужный для точности, объясни при первом существенном употреблении.
- Имена файлов, команды, кодовые идентификаторы, URLs и обозначения API
  сохраняй дословно. Не переводи их и не меняй ради оценки стиля.

## Выбор представления

| Что нужно понять | Подходящая форма |
| --- | --- |
| Один результат или короткое объяснение | Текст |
| Различия нескольких вариантов | Таблица с сопоставимыми критериями |
| Исследовать связи в материалах и показать карту | Graphify; готовый граф или его HTML/SVG — в отчете |
| Показать известные связи, порядок действий или движение данных | Схема Mermaid; при необходимости экспорт в SVG |
| Измерения, изменение значений или распределение | График с подписями и единицами |
| Сложный результат с общей картиной, деталями или полезным взаимодействием | HTML, объединяющий нужные представления |

Выбор определяется пользой для понимания. Большой объем текста сам по себе
не требует HTML, а короткий запрос может требовать схемы. Не создавай
одновременно все формы для одного результата.

Наличие связей в графе само по себе не доказывает порядок исполнения.
Для точной последовательности используй Mermaid. Выбранный экспорт должен
сохранять важные стрелки и подписи отношений.

В HTML главный вывод и существенные ограничения видны без дополнительных
действий. Подробности можно раскрывать. Связывай таблицу и график, если они
показывают одни данные; фильтры нужны только для полезного выбора или анализа.
Сохраняй читаемые подписи и нормальный порядок просмотра на узком экране.

Строй визуализацию по имеющимся данным. Указывай единицы, основание сравнения
и источник, когда они нужны для интерпретации. Предполагаемые связи обозначай
как предположения. Не выдумывай числа, измерения или выполненные проверки
для заполнения графика. Демонстрационные данные явно отмечай как пример.

Рядом с визуализацией дай краткий текстовый вывод. Для сложного графика
обеспечь доступ к основным значениям или таблице; смысл не должен зависеть
только от цвета или просмотра изображения.

Исправность файла и соответствие изображения данным подтверждаются только
реальными проверками, проведенными в рамках разрешенной работы.
Содержание кода HTML само по себе не доказывает правильность отображения.

## Рубрика для автора и проверяющего

Оценивай запрос и весь существенный результат, включая переданное содержание
материала. Применяй только относящиеся к задаче требования. Обычная реплика
не обязана содержать отчет, ссылки, ограничения или график.

| Критерий | Условие соответствия |
| --- | --- |
| `relevant` | Ответ закрывает части запроса; главный результат понятен. Запрошенные подробности сохранены. |
| `clear_russian` | Связный текст написан понятным русским; термины последовательны, лишний жаргон заменен, точные идентификаторы сохранены. |
| `concise` | Нет ненужных вступлений, повторов и отступлений. Сокращение не удалило смысл, условия или запрошенные детали. |
| `findable` | Главный вывод, состояние работы и существенные ограничения легко найти. Они не скрыты только в раскрываемых деталях. |
| `usable` | Пользователь понимает значение результата и, когда нужно, где он находится и какое действие требуется. |
| `status_precision` | Формулировки различают подготовку, внесенные изменения и реально выполненные проверки. Выводы не представлены как доказанные действия. |
| `appropriate_format` | Представление помогает понять задачу. HTML, схема или график используются по смыслу; их отсутствие не является дефектом само по себе. |
| `faithful_visuals` | Если есть визуализация, ее данные и связи согласованы с переданным основанием; предположения и примеры обозначены. |

Для каждого применимого критерия возможны «соответствует», «не соответствует»
и «недостаточно данных». Например, без переданного содержания HTML нельзя
судить о его структуре; без исходных чисел нельзя подтвердить точность графика.
Отсутствие данных у проверяющего не доказывает дефект отчета.

Текстовая оценка Jev не подтверждает фактический запуск, исполнение команд,
исправность интерфейса или истинность источника. Для таких выводов нужны
соответствующие доказательства; неоднозначный результат остается
неподтвержденным. Требования пользователя и более высокие инструкции
определяют допустимые действия.

Сам документ является рубрикой. Подключенный MCP-адаптер передает ее Jev
вместе с актуальным заданием и состоянием результата. Skill задает порядок
проверки и одной коррекции; hooks сохраняют контекст и контролируют наличие
receipt. Разрешения, ключ и бюджет задаются отдельно в локальной установке.
